# Бенчмарки

Измерения, на которых основан выбор моделей для поиска по галерее.

| Что | Где | Вопрос |
| --- | --- | --- |
| Модель CLIP/SigLIP2 (поиск по смыслу) | этот проект, `clip.ipynb` | какая модель лучше находит картинки по запросу на русском и английском и сколько это стоит на CPU |
| OCR (поиск по тексту на картинке) | [`ocr/`](ocr/README.md) | какая система лучше читает русский и английский текст на фото |

## CLIP: итоги

Crossmodal-3600, случайные 1000 картинок, 4000 запросов (ru + en), по одной правильной картинке на запрос. CPU Ryzen 5 5600H (6 ядер), без GPU, fp32.

| Модель | Recall@1 | Recall@10 | ru Recall@1 | Картинка, мс | Запрос, мс | Пик RAM, ГиБ |
| --- | --- | --- | --- | --- | --- | --- |
| `ViT-SO400M-16-SigLIP2-384` | 0,791 | 0,974 | 0,856 | 2081 | 313 | 5,3 |
| **`ViT-B-16-SigLIP2`** (в приложении) | 0,767 | 0,972 | 0,813 | 253 | 114 | 2,2 |
| `ViT-B-32-SigLIP2-256` | 0,750 | 0,969 | 0,796 | 51 | 62 | 2,1 |
| `xlm-roberta-base-ViT-B-32` | 0,718 | 0,954 | 0,779 | 81 | 133 | 3,6 |
| `nllb-clip-base-siglip` | 0,709 | 0,955 | 0,772 | 479 | 152 | 2,8 |

Выводы (подробнее в конце `clip.ipynb`): SigLIP2 заметно лучше других семейств; самая большая модель даёт +2,4 п.п. Recall@1 за 8-кратную цену, для CPU это не оправдано; `B-16` — хороший баланс; `B-32-SigLIP2-256` в 5 раз быстрее индексирует и теряет только 1,7 п.п. Recall@1.

Графики лежат в `results/cpu/figures/`, таблица — в `results/cpu/summary.csv`, сырые замеры по каждой модели — в `results/cpu/raw/*.json`.

## Как запустить

```bash
cd bench
uv sync
uv run jupyter nbconvert --to notebook --execute --inplace clip.ipynb   # или открыть clip.ipynb
# только замеры, без ноутбука:
uv run python -m bench.clip_bench run --n-images 1000 --out results/cpu
```

Первый запуск скачивает датасет (~330 МБ в `~/models/datasets/xm3600`, меняется переменной `XM3600_CACHE`) и веса моделей (несколько ГБ в кэш Hugging Face). Результаты по моделям кэшируются, повторный запуск ничего не пересчитывает (`FORCE = True` в ноутбуке или `--force` в консоли пересчитывает). Полный прогон на CPU около двух часов, из них почти час — SO400M.

Каждая модель считается в отдельном процессе, чтобы память не смешивалась. Для проверки скорости без качества можно запустить на 100 картинках: `--n-images 100 --out results/cpu_speed`.

## Что измеряется

- **Качество:** Recall@1/5/10, NDCG@10 и MRR для поиска «подпись → картинка» среди всей галереи, по всем запросам и отдельно по языкам.
- **Индексация:** время на одну картинку (чтение и ресайз + прогон модели). Это то, что приложение делает при добавлении фото.
- **Поиск:** задержка одного текстового запроса (батч 1, медиана из 30).
- **Ресурсы:** пиковая RAM процесса, сколько ядер CPU занято, число параметров.

## Ограничения

- Скорость SO400M и `nllb` замерена, пока рядом считался OCR-бенчмарк. Для `nllb` повторный замер на свободной машине дал 486 мс против 479 мс (разница меньше 2%). Повторный замер SO400M в коротком режиме дважды упал с ошибкой доступа к памяти, причину не искали, поэтому её цифры не перепроверены.
- Замер в fp32, приложение запускает модель через `torch.autocast` (на CPU это bfloat16): абсолютные цифры в приложении могут отличаться.
- Галерея из 1000 фото: в большой галерее Recall@K ниже у всех, порядок моделей, скорее всего, сохранится.
- Подписи описывают сцену. Качество поиска по тексту на картинках проверяет OCR-бенчмарк, не этот.
- Сначала в `clip.ipynb` была ошибка: подписи и разметка собирались в разном порядке, и все модели получали случайный результат (Recall@1 = 0,002). Теперь подписи и номера картинок строятся одним циклом (`src/bench/data.py`), а `clip_bench.py` предупреждает, если Recall@10 оказывается близок к случайному.
