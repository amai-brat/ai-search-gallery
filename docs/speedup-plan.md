# План ускорения и одно приложение без Docker

Итоги бенчмарков из ветки `feat/benchmarks` и план работ. С документа можно начать отдельную сессию: здесь цифры, где лежит код, порядок шагов и как проверять каждый шаг.

## Цель

Сервис должен индексировать и искать в разы быстрее на обычном ноутбуке, только на CPU, и запускаться одной командой без Docker. Интерфейс остаётся во вкладке браузера.

Критерии готовности:

- индексация на CPU как минимум в 3 раза быстрее базовой линии этапа 0 (по общему времени на наборе `bench/e2e`);
- поиск по смыслу доступен вскоре после начала индексации (CLIP идёт первым проходом);
- CLIP: Recall@1 на XM3600 падает не больше чем на 2 п.п. относительно текущих 0,767;
- OCR: доля найденных слов на реальных фото не ниже текущей (0,68) с допуском 2 п.п., на синтетике не ниже 0,93;
- в зависимостях бэкенда нет `torch`, `open-clip-torch`, `timm`, `transformers`, `paddlepaddle`, `paddleocr`;
- для запуска не нужны Docker, Postgres, Redis и Node.js (Node нужен только для сборки фронтенда).

Видеокарта в этот план не входит: ничего для GPU не ставим. Позже её можно добавить заменой пакета `onnxruntime` на `onnxruntime-directml` (пакет примерно того же размера, без CUDA), код под это не должен мешать.

## Что уже известно из бенчмарков

### CLIP (поиск по смыслу)

XM3600, 1000 картинок, 4000 запросов (en + ru), CPU Ryzen 5 5600H, fp32. Подробно в `bench/README.md` и `bench/clip.ipynb`.

| Модель | Recall@1 | Recall@10 | Картинка, мс | Запрос, мс | Пик RAM, МиБ |
|---|---|---|---|---|---|
| ViT-SO400M-16-SigLIP2-384 | 0,791 | 0,974 | 2081 | 313 | 5410 |
| **ViT-B-16-SigLIP2 (сейчас в приложении)** | 0,767 | 0,972 | 253 | 114 | 2205 |
| **ViT-B-32-SigLIP2-256 (кандидат)** | 0,750 | 0,969 | **51** | 62 | 2183 |
| xlm-roberta-base-ViT-B-32 | 0,718 | 0,954 | 81 | 133 | 3648 |
| nllb-clip-base-siglip | 0,709 | 0,955 | 479 | 152 | 2900 |

Семейство SigLIP2 лучше остальных. B-32-SigLIP2-256 кодирует картинку в 5 раз быстрее B-16 и теряет 1,7 п.п. Recall@1. Обе дают вектор 768, но векторы разные: при смене модели нужна полная переиндексация, а окна `SEMANTIC_WINDOW_*` подбираются заново.

### OCR (текст на картинке)

Синтетика ru/en, реальные фото, доски, фото без текста. Подробно в `bench/ocr/README.md` и `bench/ocr/ocr.ipynb`.

| Система | Слова, синтетика ru | Слова, реальные фото | мс/картинку (6 потоков) |
|---|---|---|---|
| **PaddleOCR mobile det + eslav rec (сейчас)** | 0,944 | **0,681** | **1231** |
| PaddleOCR mobile det + cyrillic rec | 0,947 | 0,553 | 1319 |
| PaddleOCR server det + eslav rec | 0,998 | 0,639 | 11789 |
| PaddleOCR v3 cyrillic | 0,407 | 0,414 | 1166 |
| EasyOCR | 0,929 | 0,556 | 2447 |

Модели OCR менять не нужно, нужно менять среду выполнения. Модели крошечные (единицы МБ), а 1,2 с на картинку объясняются тем, что Paddle работает на CPU с выключенным MKLDNN, в самом медленном режиме.

Разовый эксперимент: уменьшение картинки до 960 px по длинной стороне перед OCR даёт −23% времени при почти том же качестве на картинках до 1280 px. На фото с телефона (4000 px) выигрыш должен быть заметно больше: детектор PaddleOCR по умолчанию не уменьшает большие картинки.

## Как устроено сейчас

- `backend/src/utils/ml_core.py`: open_clip + torch, модель грузится лениво, картинки по одной, только CPU. Модель загружает и процесс API (для кодирования запроса), поэтому первый поиск после старта медленный.
- `backend/src/utils/ocr.py`: PaddleOCR 3.x, `PP-OCRv5_mobile_det` + `eslav_PP-OCRv5_mobile_rec`, без поворотов и выпрямления, MKLDNN выключен.
- `backend/src/worker.py`: Celery-задача (`--pool=solo`), файлы строго по очереди: sha256, CLIP, OCR. Файл читается и декодируется дважды (PIL для CLIP, Paddle для OCR). EXIF-поворот не применяется.
- `backend/src/features/images/get_image_file.py`: миниатюры создаются при первом показе из полноразмерного файла.
- Хранение: Postgres + pgvector (HNSW) и `pg_trgm`/`to_tsvector` для OCR-поиска, Redis как брокер Celery, всё в Docker.
- Окружение бэкенда весит 1,5 ГБ.

## Целевая схема

Один процесс Python, запуск одной командой (позже exe), открывает вкладку браузера:

```
uv run gallery  →  http://127.0.0.1:8000

┌──────────────────── один процесс ─────────────────────┐
│ FastAPI: API + собранный фронтенд (статика)            │
│ Поиск: векторы всех картинок в памяти (numpy)          │
│ Индексатор (фоновый поток):                            │
│   чтение файла → одна уменьшенная копия                │
│     ├→ CLIP пакетами по 8–16 → в базу (поиск уже есть) │
│     ├→ миниатюра                                       │
│     └→ OCR в 2 параллельных потоках → в базу           │
│ ONNX Runtime (CPU)                                     │
│ SQLite-файл в %LOCALAPPDATA%                           │
└────────────────────────────────────────────────────────┘
```

Откуда ожидается ускорение (оценки, проверяются замерами):

| Что меняем | Сейчас | Ожидание |
|---|---|---|
| OCR: Paddle → ONNX Runtime (RapidOCR, те же модели PP-OCRv5) | ~1,2 с | ~0,3 с |
| OCR: уменьшение до 960 px | — | ещё −25–50%, больше на фото с телефона |
| Одно декодирование, сразу уменьшенное (`Image.draft` для JPEG) | 2 полных | 1 быстрое |
| CLIP: torch → ONNX Runtime, пакетами | ~0,25 с | ~0,15 с (B-32-256 ~0,05 с) |
| Конвейер: декодирование, CLIP и OCR параллельно | 1 картинка за раз | ×1,5–2 пропускной способности |
| Два прохода: CLIP по всем, потом OCR | поиск после полной обработки | поиск по смыслу через 1–2 минуты |
| «Обновить» папку: пропуск по размеру и дате изменения | sha256 каждого файла | почти мгновенно |
| Миниатюры при индексации | из оригинала при первом показе | галерея сразу быстрая |
| Старт без Docker и torch, прогрев модели | десятки секунд, медленный первый поиск | несколько секунд |

## План работ

Этапы 1–3 не трогают базу и Celery: функции `get_image_embedding`, `get_text_embedding`, `get_image_text` сохраняют сигнатуры, меняется начинка. Так ускорение и отказ от Docker проверяются отдельно. После каждого этапа сквозной замер.

### Этап 0. Базовая линия

1. Набор `bench/e2e/data` (в git не попадает): `test-images` (42, до 1280 px), синтетика из `bench/ocr/data/images` (150, 1024×768) и «фото с телефона»: реальные фото из `test-images`, увеличенные до 4032 px по длинной стороне. Пиксели у них ненастоящие, но для времени декодирования и детектора важен размер, а качество OCR проверяется в `bench/ocr`.
2. Скрипт `backend/scripts/bench_indexing.py`: вызывает те же функции, что и воркер, пишет время sha256, CLIP, OCR на картинку, время загрузки моделей, пик памяти, распознанный текст и векторы (чтобы сравнивать новые реализации со старой).
3. Записать результат для текущего кода в `bench/e2e/results/baseline.json` и в этот документ.

### Этап 1. OCR на ONNX Runtime

1. Проверка за день: есть ли у RapidOCR готовые ONNX-модели PP-OCRv5 mobile det и eslav rec. Если eslav нет, сконвертировать через `paddle2onnx` из модели в кэше (`~/.cache/huggingface/hub/models--PaddlePaddle--eslav_PP-OCRv5_mobile_rec`) вместе со словарём символов.
2. Те же стадии и пороги детектора, что у PaddleOCR; классификатор ориентации строк выключен.
3. Уменьшение до 960 px по длинной стороне перед детектором.
4. Система `rapidocr-eslav` (и вариант с ресайзом) в `bench/ocr/ocr_bench.py`, прогон `run` и `speed`. Критерий: качество в пределах 2 п.п. от `paddle-current`. Если хуже, сравнить боксы и строки с PaddleOCR и найти расходящийся этап.
5. Заменить `utils/ocr.py`, сквозной замер.

### Этап 2. CLIP на ONNX Runtime

1. Сначала проверить готовые ONNX-экспорты SigLIP2 от Immich на Hugging Face (визуальный и текстовый энкодеры отдельно, токенизатор, конфиг предобработки) и их лицензию. Иначе экспорт из open_clip (`torch.onnx.export`, opset 17+, динамическая ось батча), torch при этом нужен только в окружении бенчмарка.
2. Предобработка на Pillow/numpy, параметры из `preprocess` open_clip. Токенизатор: библиотека `tokenizers` по `tokenizer.json`; токены должны совпадать с open_clip на русских запросах, включая длину контекста и паддинг.
3. Совпадение векторов torch и ONNX: косинус больше 0,999 на 100 картинках и 100 запросах (векторы базовой линии этапа 0).
4. ONNX-вариант в `bench/src/bench/clip_bench.py`, прогон XM3600 для B-16 и B-32-256, выбор модели по умолчанию.
5. Таблица эмбеддингов текстового энкодера (словарь 256 тыс. токенов, ~0,8 ГБ в fp32) в fp16 или int8, если бенчмарк не показывает потерь.
6. Пакетное кодирование картинок, кэш векторов запросов, прогрев модели при старте API.
7. Заменить `utils/ml_core.py`, удалить torch, open_clip, timm, transformers, paddle из `backend/pyproject.toml`, замерить размер окружения.

### Этап 3. Индексатор-конвейер

1. Одно декодирование файла: `ImageOps.exif_transpose`, для JPEG `Image.draft` до нужного размера; из этой копии вход CLIP, вход OCR (960 px) и миниатюра.
2. Два прохода: сначала CLIP по всем новым файлам (запись без OCR), потом OCR. Воркер уже умеет дозаполнять запись без OCR.
3. Параллельность: пул потоков на чтение и декодирование, CLIP пакетами, OCR в 2 сессиях. Число потоков ONNX Runtime на сессию подобрать замером.
4. Пропуск неизменённых файлов по пути, размеру и mtime без sha256 (нужны колонки `size` и `mtime`).
5. Миниатюры при индексации.

### Этап 4. Без Docker

1. SQLite (WAL) вместо Postgres: векторы как BLOB float32, поиск умножением матриц в numpy по всей коллекции в памяти (10 тыс. картинок около 30 МБ, единицы миллисекунд).
2. OCR-поиск: `LIKE` в SQLite не различает регистр только у латиницы, поэтому хранить нормализованный текст (нижний регистр, ё→е) и колонку основ слов через `snowballstemmer` (ru + en) вместо `to_tsvector`. Парсер `utils/search_query.py` не меняется, переписывается только `_compile`.
3. Фоновый поток-индексатор вместо Celery и Redis, таблица `index_jobs` и сброс зависших задач при старте остаются.
4. FastAPI раздаёт собранный фронтенд (`npm run build` → `StaticFiles`), один порт, без CORS.
5. Команда `gallery` (точка входа в `pyproject.toml`): поднимает сервер и открывает вкладку браузера. Данные в `%LOCALAPPDATA%\AISearchGallery`, модели скачиваются при первом запуске. Обновить `scripts/*.ps1` и README, `compose.yml` удалить.
6. Ручная проверка в веб-интерфейсе: индексация папки, загрузка файлов, поиск на русском и английском, OCR-запросы с `AND`/`OR`/`NOT` и формами слов.

### Этап 5 (по желанию). Exe

PyInstaller (onedir) и при желании установщик Inno Setup; поведение то же, открывается вкладка браузера.

## Как запускать бенчмарки

Сквозной замер (окружение бэкенда):

```bash
cd backend
uv run python scripts/bench_indexing.py make-dataset
uv run python scripts/bench_indexing.py run --label baseline
```

CLIP и OCR по отдельности: окружения и датасеты удалены ради места, при первом запуске скачаются заново (XM3600 около 0,75 ГБ).

```bash
cd bench
python -m uv sync
python -m uv run python -m bench.clip_bench run --n-images 1000 --out results/cpu
```

```bash
cd bench/ocr
python -m uv sync
python -m uv run python make_dataset.py
python -m uv run python ocr_bench.py run --threads 2
python -m uv run python ocr_bench.py speed --threads 6
```

Скорость мерить на свободной машине.

## Результаты замеров

Полный отчёт с графиками для презентации: [bench/e2e/README.md](../bench/e2e/README.md).

Сквозной замер `bench/e2e` (224 картинки: 42 из `test-images`, 150 синтетических, 32 «фото с телефона» 4032 px), Ryzen 5 5600H, только CPU. Медиана на картинку, мс. Результаты в `bench/e2e/results/{baseline,onnx}.json`.

| Группа | CLIP до | CLIP после | OCR до | OCR после | Всего до | Всего после | Ускорение |
|---|---|---|---|---|---|---|---|
| small (до 1280 px) | 4577 | 178 | 1369 | 164 | 6051 | 346 | ×17 |
| synthetic (1024×768) | 4799 | 190 | 1186 | 189 | 6064 | 382 | ×16 |
| phone (4032 px) | 4706 | 192 | 12782 | 255 | 17777 | 448 | ×40 |

- Весь набор: 1790 с → 94 с (**×19**), 8 → 143 картинки в минуту.
- Запрос поиска: 1556 → 55 мс; загрузка моделей: CLIP 8,6 → 0,7 с, OCR 4,4 → 1,2 с.
- Пик памяти скрипта замера (оба энкодера CLIP и OCR в одном процессе): 6785 → 2333 МиБ. В приложении воркер грузит только визуальный энкодер, API только текстовый.
- Окружение бэкенда: 1,5 ГБ → 389 МБ (модели отдельно: CLIP 1,5 ГБ, OCR 13 МБ в `backend/models`).

Главная находка этапа 0: CLIP в приложении шёл не 0,25 с, как в бенчмарке, а 4,8 с на картинку. `torch.amp.autocast("cpu")` в старом `ml_core.py` переводил вычисления в bfloat16, который этот процессор эмулирует (отдельная проверка: 168 мс в fp32 против 1464 мс с autocast). Бенчмарк CLIP считал без autocast и этого не видел.

Проверка качества:

- CLIP: ONNX-экспорт Immich совпадает с open_clip fp32 (косинус 1,00000 на 36 картинках и 18 запросах, токены совпали на всех запросах, включая русские, «ё», пунктуацию и длинные). С быстрым декодированием JPEG (`Image.draft`) и EXIF-поворотом косинус не ниже 0,99925. Recall на XM3600 поэтому не пересчитывался.
- OCR (`bench/ocr`, система `rapid-eslav-960-nodil`, она и стоит в приложении):

| Система | Доски | Реальные фото | Синтетика en | Синтетика ru | CER | Мусор | мс |
|---|---|---|---|---|---|---|---|
| paddle-current (было) | 0,900 | 0,681 | 0,954 | 0,944 | 0,042 | 2,3 | 1812 |
| rapid-eslav (те же настройки) | 0,900 | 0,625 | 0,977 | 0,947 | 0,039 | 1,9 | 220 |
| **rapid-eslav-960-nodil (стало)** | 0,900 | 0,625 | **0,986** | **0,960** | **0,031** | 1,9 | 193 |

  На реальных фото (их 12) разница в одном слове: «ПРОДОВОЛЬСТВЕННЫЙ» прочитано как «…ЫИ». Поиск с формами слов его всё равно находит. Формально критерий «в пределах 2 п.п.» не выполнен, но выборка слишком мала, чтобы считать это ухудшением; на синтетике стало лучше. Расширение маски детектора (`use_dilation`, по умолчанию включено в RapidOCR, у Paddle выключено) портило русский текст, поэтому выключено.

Сделано: этап 0, этап 1, этап 2 (кроме fp16 текстового энкодера и выбора B-32-256; у экспортов Immich фиксированный размер пакета 1, поэтому пакеты идут по одной картинке, на CPU это почти не влияет: 160 против 159 мс). Дальше: этап 3 (конвейер, два прохода, миниатюры, пропуск по mtime) и этап 4 (без Docker).

## Риски и открытые вопросы

- Токенизатор Gemma без `transformers`: если токены разойдутся, русские запросы молча станут хуже. Проверять на русских запросах.
- eslav-распознаватель в ONNX: готового может не быть, `paddle2onnx` иногда ломается на новых операторах.
- B-32-256 или B-16 по умолчанию: решить по цифрам этапа 2.
- Параллельные потоки индексации и поиск в одном процессе: если поиск во время индексации заметно тормозит, вынести индексатор в дочерний процесс.
- Перенос уже проиндексированных данных из Postgres в SQLite не планируется: после смены модели всё равно нужна переиндексация.
